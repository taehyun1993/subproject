# Golf Reservation Concurrency Problem

## 1. 배경

현재 예약 도메인은 여러 개의 골프존과 여러 개의 타석을 가진다. 각 타석은 고유한 식별자를 가진다. 예약은 1분 단위로 가능하며, 동일한 타석에 대해서는 예약 시간이 절대 겹치면 안 된다.

다른 타석은 같은 시간대 예약이 가능하다. 따라서 동시성 제어의 기준은 골프존 전체가 아니라 개별 타석이다.

## 2. 핵심 요구사항

- 동일한 `bay_id`에 대해 예약 시간 구간이 겹치면 안 된다.
- 예약 가능 단위는 1분이다.
- 서로 다른 `bay_id`는 같은 시간대 예약이 가능하다.
- 정상 상황에서는 Redis를 이용해 빠르게 타석 단위 락을 획득한다.
- Redis 장애 상황에서는 MariaDB 기반 fallback으로 예약 정합성을 유지한다.
- Redis 장애가 API 전체 지연으로 전파되지 않도록 circuit breaker를 둔다.
- 락 대기와 락 점유에는 타임아웃이 있어야 한다.

## 3. 시간 구간 충돌 정의

새 예약 요청이 다음 값을 가진다고 하자.

```text
new_start_at
new_end_at
```

기존 예약과 충돌하는 조건은 다음과 같다.

```sql
existing.start_at < :new_end_at
AND existing.end_at > :new_start_at
```

예시:

```text
기존 예약: 10:00 ~ 11:00

충돌:
- 10:00 ~ 10:30
- 10:30 ~ 11:30
- 10:59 ~ 11:30

비충돌:
- 09:00 ~ 10:00
- 11:00 ~ 12:00
```

여기서 종료 시각은 exclusive로 취급한다. 즉 `10:00 ~ 11:00`과 `11:00 ~ 12:00`은 겹치지 않는다.

## 4. 단순 중복 조회의 문제

아래 쿼리만으로는 동시성 안전성을 보장할 수 없다.

```sql
SELECT 1
FROM reservation
WHERE bay_id = :bay_id
  AND status IN ('RESERVED', 'PAID')
  AND start_at < :new_end_at
  AND end_at > :new_start_at
LIMIT 1;
```

동시에 두 요청이 들어오면 다음 race condition이 발생할 수 있다.

```text
T1: 중복 예약 없음 확인
T2: 중복 예약 없음 확인
T1: 예약 INSERT
T2: 예약 INSERT
```

따라서 중복 조회는 필요하지만, 그 자체가 정합성 보장 수단은 아니다. 같은 타석에 대한 예약 생성 흐름을 직렬화한 뒤 중복 조회를 수행해야 한다.

## 5. 현재 성능 가정

현재 예약 처리 시간은 약 67ms로 측정되었다.

단순 계산:

```text
1 server TPS ~= 1000ms / 67ms ~= 14.9 TPS
6 servers TPS ~= 89.5 TPS
```

이 값은 Redis 응답 시간, MariaDB 커넥션 풀, 트랜잭션 시간, JVM 상태, 네트워크 지연에 따라 달라진다. 문서에서는 대략 90 TPS 수준의 기준값으로만 사용한다.

## 6. 설계 관점의 핵심

이 문제는 "예약 row를 어떻게 조회할 것인가"보다 "같은 타석의 예약 생성을 어떻게 직렬화할 것인가"가 핵심이다.

```text
같은 bay_id:
  동시에 하나의 예약 생성 흐름만 통과

다른 bay_id:
  서로 독립적으로 처리
```

따라서 락 키와 fallback DB 락의 단위는 모두 `bay_id`여야 한다.
