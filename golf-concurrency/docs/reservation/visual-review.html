Golf Reservation Concurrency Review

같은 타석의 겹치는 예약을 막기 위한 Redis 락, MariaDB fallback, circuit breaker 설계를 리뷰용으로 압축한 시각 자료.

1분 단위 예약 타석 단위 직렬화 Redis 정상 경로 DB fallback

Problem Frame

문제는 예약 row 조회가 아니라 같은 타석의 예약 생성 흐름을 직렬화하는 것이다. 다른 타석은 병렬 처리되어야 한다.

0 허용 가능한 동일 타석 중복 예약 수
1 min 예약 가능한 최소 시간 단위
bay_id 락과 직렬화의 기준 식별자
~90 TPS 67ms, 서버 6대 기준 단순 추정

Normal Path

Redis가 정상일 때는 DB row lock을 항상 잡지 않는다. Redis 락으로 같은 타석의 요청만 애플리케이션 앞단에서 직렬화한다.

1. Request

사용자가 특정 타석과 시간 구간으로 예약을 요청한다.

2. Redis Lock

`reservation:lock:bay:{bayId}`를 `SET NX PX`로 획득한다.

3. Overlap Check

같은 타석의 기존 예약과 시간 구간 충돌을 조회한다.

4. Insert

충돌이 없으면 예약 row를 생성한다.

5. Unlock

Lua script로 token이 일치할 때만 Redis key를 삭제한다.

Failure Path

Redis command timeout과 장애가 반복되면 circuit breaker가 Redis 접근을 차단한다. 이때 MariaDB의 `bay_lock` row가 직렬화 지점이 된다.

Circuit OPEN
Skip Redis OPEN 상태에서는 Redis lock 시도를 생략한다.
Start Transaction 예약 생성에 필요한 DB 작업만 짧게 묶는다.
SELECT FOR UPDATE `bay_lock` row를 잡아 같은 타석 요청을 대기시킨다.
Commit or Rollback 트랜잭션 종료 시 DB row lock은 자동 해제된다.

CLOSED

Redis 정상으로 보고 Redis lock을 사용한다.

OPEN

Redis 장애로 보고 일정 시간 Redis 접근을 생략한다.

HALF_OPEN

제한된 요청만 Redis를 시험하고 성공 시 CLOSED로 복귀한다.

Timeout Map

가장 중요한 운영 포인트는 timeout을 섞지 않는 것이다. Redis 장애 감지, 락 대기, 락 자동 해제, DB row lock 대기는 서로 다른 값이다.

Redis Command

Redis 명령 1회의 응답 대기. 예: 50~200ms.

Lock Wait

Redis는 정상이나 다른 요청이 lock 보유. 예: 10s.

Lock TTL

소유 서버 장애 시 자동 해제. P99 처리 시간 + 여유.

DB Lock Wait

`SELECT FOR UPDATE` 대기. 예: 3s.

Transaction

예약 DB 트랜잭션 전체 시간. 외부 API는 제외.

ADR Summary

리뷰에서 가장 자주 나올 질문은 "왜 이 방식인가"다. 아래는 채택/비채택 이유를 압축한 것이다.

Selected

  • 정상 경로: Redis lock only
  • 장애 경로: MariaDB `SELECT FOR UPDATE` fallback
  • Redis 장애 전파 방지: circuit breaker
  • 락 단위: `bay_id`
정상 성능과 장애 대응의 균형이 좋음

Rejected For Now

  • 1분 slot row 테이블: write amplification이 큼
  • Redis + DB lock 항상 사용: 중복 락 비용
  • DB lock only: 모든 경합이 DB로 집중
  • Redisson RLock: 추상화가 두꺼워 초기 설계 통제력이 낮음
트래픽과 경쟁 수준 대비 과한 선택은 보류
