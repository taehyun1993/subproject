# AI 개발 팀 워크플로 가이드

이 문서는 작업 유형에 따라 어떤 역할을 어떤 순서로 사용할지 정의한다. 모든 작업이 모든 역할을 거치지 않는다. 작업 유형을 먼저 파악하고, 해당 유형의 흐름을 따른다.

---

## 1. 작업 유형 판단

작업이 들어오면 먼저 유형을 구분한다.

| 유형 | 판단 기준 |
| --- | --- |
| 신규 개발 | 새로운 기능, 새로운 화면, 새로운 서비스 흐름 |
| 레거시 추가 개발 | 기존 기능에 새 기능 추가, 기존 흐름 확장 |
| 버그 수정 | 현재 동작이 의도와 다름 |
| 디자인 변경 | 기능 변경 없이 화면, 문구, UX 흐름만 변경 |
| 리팩터링 | 동작은 보존하고 구조·중복·책임만 개선 (회귀 검증 필수) |
| 성능 개선 | 동작은 유지하고 응답·렌더링·자원 사용만 개선 |
| 외부 연동 변경 | 결제·문자·배송 등 외부 API 연동 추가·변경 |

유형이 섞인 경우(예: 버그 수정 + 정책 변경)는 주된 목적을 기준으로 유형을 정하고, 필요한 단계를 조합한다.

위 표에 깔끔히 들어가지 않는 유지보수성/성능/연동 작업은 해당 역할 문서의 작업 유형 기준을 직접 따른다(백엔드: `backend_developer.md` §4·§13·§14, 프론트: `frontend_developer.md` §4·§12). 리팩터링은 "기존 동작 보존 + 회귀 검증 필수"를 공통 원칙으로 한다.

---

## 2. 공통 진입 단계

작업 유형을 정한 뒤 바로 구현하지 않는다. 먼저 공통 진입 단계를 거쳐 필요한 역할과 확인 범위를 정한다.

### 확인 항목

| 항목 | 확인 내용 |
| --- | --- |
| 요청 요약 | 사용자가 원하는 결과를 한두 문장으로 정리한다 |
| 작업 유형 | 신규 개발 / 레거시 추가 개발 / 버그 수정 / 디자인 변경 중 무엇인지 판단한다 |
| 영향 영역 | 기획, UI/UX, 프론트엔드, 백엔드, DB, 운영 중 어디에 영향이 있는지 확인한다 |
| 필요한 역할 | 반드시 필요한 역할과 생략 가능한 역할을 정한다 |
| 포함 범위 | 이번 작업에서 반드시 처리할 내용을 정한다 |
| 제외 범위 | 이번 작업에서 처리하지 않을 내용을 정한다 |
| 미정 사항 | 확인이 필요한 정책, 화면, API, 데이터 조건을 기록한다 |
| 검증 방법 | 테스트, 빌드, 브라우저 확인, API 확인 등 필요한 검증을 정한다 |
| 피드백 기준 | 작업 종료 시 피드백 점검이 필요한지 확인한다 |

### 진입 단계 산출물

```markdown
## 작업 진입 요약
- 작업 유형:
- 요청 요약:
- 영향 영역:
- 필요한 역할:
- 생략 역할과 근거:
- 포함 범위:
- 제외 범위:
- 미정 사항:
- 검증 방법:
- 피드백 기준:
```

작업이 아주 작고 명확하면 이 내용을 길게 문서화하지 않아도 된다. 다만 역할을 생략하거나 검증을 생략하는 경우에는 근거를 남긴다.

이 진입 요약은 §3~§6의 첫 역할(기획자/백엔드 등)에게 **공통 입력**으로 전달된다. 특히 `미정 사항`과 `검증 방법`은 첫 역할이 인수해서 해소하거나, 해소하지 못하면 다음 단계로 명시적으로 이월한다(머릿속에만 두지 않는다). 각 역할이 "받아야 할 입력 항목"은 `planner.md` §13, `ui_ux_designer.md` §13, `backend_developer.md` §6과 이 진입 요약을 함께 본다.

## 3. 신규 개발

### 언제

기획 문서 또는 아이디어가 있고, 새로운 기능 또는 화면을 처음 만드는 경우.

### 흐름

```
기획자 → UI/UX 디자이너 → 백엔드 개발자
                        → 프론트엔드 개발자
```

백엔드와 프론트엔드는 디자이너 산출물이 확정된 후 병렬로 진행할 수 있다.

### 단계별 역할과 산출물

| 단계 | 역할 | 입력 | 산출물 |
| --- | --- | --- | --- |
| 1 | 기획자 | 아이디어, 요구사항, 도메인 지식 | 확정 기획 문서 (목적, 사용자 흐름, 기능 요구사항, 정책, 완료 조건) |
| 2 | UI/UX 디자이너 | 확정 기획 문서 | 화면 구조, 사용자 흐름, 상태별 UI, 개발 핸드오프 기준 |
| 3 | 백엔드 개발자 | 확정 기획 문서, UI/UX 산출물 | API 명세, 데이터 모델, 상태/정책 설계, 구현, 운영 절차(배포·롤백·마이그레이션 순서, DB 변경 시) |
| 3 | 프론트엔드 개발자 | 확정 기획 문서, UI/UX 산출물, API 명세 | 화면 구현, 상태 처리, API 연동 |

### 주의사항

- 기획이 미정 사항이 많은 상태에서 개발을 시작하지 않는다.
- UI/UX 산출물에서 필요한 데이터와 화면 상태가 드러난 뒤 API 명세 초안을 맞추면 병렬 진행이 안정적이다.
- 백엔드는 UI/UX 확정 전이라도 데이터, 정책, 외부 연동, 성능 제약이 명확한 경우 사전 의견을 줄 수 있다. 이때 API 명세를 확정하지는 않는다.
- 기획이 바뀌면 디자이너와 개발자 모두에게 영향 범위를 공유한다.

## 4. 레거시 추가 개발

### 언제

기존 기능이나 화면에 새 기능을 추가하거나 기존 흐름을 확장하는 경우. 기존 코드, 도메인 지식, 데이터 구조를 먼저 파악해야 한다.

### 흐름

```
백엔드 개발자 (코드/DB 분석)
  → 기획자 (정책 정리, 범위 확정)
    → UI/UX 디자이너 (화면 변경 있을 때만)
    → 백엔드 개발자 (구현)
    → 프론트엔드 개발자 (화면 변경 있을 때만)
```

화면 변경이 없으면 디자이너와 프론트엔드는 생략한다.

### 단계별 역할과 산출물

| 단계 | 역할 | 입력 | 산출물 |
| --- | --- | --- | --- |
| 1 | 백엔드 개발자 | 기존 코드베이스, 기존 DB 구조, 도메인 지식 | 현재 구조 분석 요약, 추가 가능 범위, 제약 사항 |
| 2 | 기획자 | 분석 요약, 요구사항 | 추가 범위 확정, 정책 정리, 완료 조건 |
| 3 | UI/UX 디자이너 | 확정 기획, 기존 화면 패턴 | 변경 화면 구조, 기존 패턴 기반 추가안 |
| 4 | 백엔드 개발자 | 확정 기획, UI/UX 산출물 | 구현, API 변경, DB 변경, 운영 절차(배포·롤백·마이그레이션 순서, DB 변경 시) |
| 4 | 프론트엔드 개발자 | 확정 기획, UI/UX 산출물, API 변경 내용 | 화면 수정, API 연동 |

> DB·데이터 변경이 포함되면 진입 산출물에 **사전 백업 가능성·롤백·검증 쿼리**를 함께 정리한다. 조직 정책상 운영 DB의 DML/DDL·마이그레이션은 **작성·리뷰까지가 AI 범위**이며, 실제 실행은 담당자에게 핸드오프한다(`backend_developer.md` §11·§15).

### 주의사항

- 기존 코드와 DB를 분석하지 않고 바로 기획/설계로 넘어가지 않는다.
- 기존 구조의 제약이 기획에 영향을 주므로 분석 결과를 기획자에게 먼저 공유한다.
- 기존 패턴을 깨는 변경이 필요하면 그 이유와 영향을 명확히 한다.

## 5. 버그 수정

버그는 성격에 따라 흐름이 달라진다. 먼저 버그 유형을 구분한다.

### 5-1. 단순 오류

**언제**: 명백한 코드 오류, 잘못된 조건문, UI 깨짐, 단순 데이터 처리 오류.

**흐름**

```
백엔드 또는 프론트엔드 개발자 (재현 → 원인 → 수정 → 회귀 테스트)
```

기획자나 디자이너 개입 없이 개발자가 직접 처리한다.

---

### 5-2. 정책적 오류

**언제**: 코드는 의도대로 동작하지만 정책이 잘못 구현된 경우. 또는 정책 자체가 불명확해서 어떤 동작이 맞는지 확인이 필요한 경우.

**흐름**

```
백엔드 개발자 (코드 분석 → 정책 불일치 확인)
  → 기획자 (정책 확인, 올바른 동작 정의)
    → 백엔드 개발자 (정책 기준으로 수정)
    → 프론트엔드 개발자 (화면 영향 있을 때만)
```

**주의사항**

- "정책적으로 맞는 동작"을 개발자가 임의로 결정하지 않는다.
- 정책 확인 없이 수정하면 다른 흐름에서 다른 버그가 생길 수 있다.

---

### 5-3. 코드/DB 분석이 필요한 오류

**언제**: 원인이 불명확하고, 재현이 어렵거나, 여러 레이어에 걸쳐 있는 경우.

**흐름**

```
버그가 위치한 레이어의 개발자 (재현 → 코드 분석 → DB/상태 분석 → 원인 파악)
  → 원인에 따라 5-1(단순 오류) 또는 5-2(정책적 오류) 흐름으로 분기
  → (원인이 화면/디자인이면 §6 디자인 변경으로도 분기)
```

진입 주체는 버그가 위치한 레이어로 정한다. 서버/DB/정책 원인이면 백엔드, 화면/상태 관리/렌더링/브라우저/라우팅 원인이면 프론트엔드가 분석을 주관한다(프론트 복잡 버그 분석 기준은 `frontend_developer.md` §4).

**분석 산출물**

- 버그 재현 조건
- 원인 위치와 원인
- 영향 범위
- 수정 방향과 리스크
- 회귀 범위(영향받는 다른 흐름·화면)

---

### 5-4. 긴급 핫픽스 (운영 영향)

**언제**: 운영 중인 서비스가 중단되거나 결제·정산·데이터에 즉시 피해가 발생하는 상황.

일반 버그 수정과 시간축이 다르다. **먼저 피해를 멈추고, 근본 수정은 그 다음**이다.

**흐름**

```
1. 즉시 완화 (롤백 또는 기능 차단·우회) → 피해 중단
2. 원인 분석 (5-3 흐름 재사용)
3. 근본 수정 (5-1 또는 5-2 흐름)
4. 사후 회귀 테스트 + 모니터링 확인
5. feedback-log에 '높음'으로 기록
```

**주의사항**

- 완화 단계에서도 §9 운영 항목(롤백·로그·모니터링)을 확인한다. 조직 정책상 인프라·운영 DB 직접 변경은 금지이므로, 완화도 코드 배포·기능 플래그·담당자 핸드오프 범위에서 한다.
- 완화와 근본 수정을 분리해 기록한다. 완화는 임시 조치이므로 근본 수정 전까지 `보류`로 추적한다.
- 보안 사고는 이 흐름에 "영향 평가 + 비공개 처리(노출 범위 확인, 로그·자격증명 회수)"를 더한 변형으로 다룬다.
- 운영 대응 세부 기준은 `backend_developer.md` §15를 따른다.

## 6. 디자인 변경

### 언제

기능 변경 없이 화면 구조, 문구, UX 흐름, 시각적 구성만 바꾸는 경우.

### 흐름

```
UI/UX 디자이너 (변경 설계)
  → 프론트엔드 개발자 (구현)
```

기획 변경이 없고 API 변경도 없으면 기획자와 백엔드는 개입하지 않는다.

### 단계별 역할과 산출물

| 단계 | 역할 | 입력 | 산출물 |
| --- | --- | --- | --- |
| 1 | UI/UX 디자이너 | 현재 화면, 변경 요청, 기존 디자인 패턴 | 변경 화면 구조, 상태별 UI, 개발 핸드오프 |
| 2 | 프론트엔드 개발자 | UI/UX 산출물, 기존 코드 | 화면 수정 구현 |

### 주의사항

- 디자인 변경이 기획 정책에 영향을 주면 기획자를 먼저 확인한다.
- 디자인 변경이 API 응답 구조 변경을 요구하면 백엔드 개발자를 포함한다.
- 기존 컴포넌트 재사용 가능 여부를 먼저 확인한다.

## 7. 작업 진행상황 확인

작업 진행상황은 현재 단계, 담당 역할, 산출물, 미정 사항 기준으로 확인한다.

### 상태 값

| 상태 | 의미 | 진입 조건 | 해제 조건 / 주체 |
| --- | --- | --- | --- |
| 대기 | 아직 시작하지 않음 | 단계가 아직 시작 전 | 담당 역할이 작업 시작 |
| 진행 중 | 현재 작업 중 | 담당 역할이 착수 | 산출물 완성 또는 막힘 발생 |
| 검토 필요 | 사용자/기획/디자인/개발 판단이 필요함 | 진행 중 판단이 막힘 | **사용자 또는 해당 역할의 결정**으로 해제 |
| 보류 | 외부 결정이나 선행 작업을 기다림 | 외부 의존이 생김 | 의존 해소 시 사용자 또는 담당 역할이 해제 |
| 완료 | 산출물과 검증이 끝남 | §9 완료 기준 충족 | (종료) |

`검토 필요`·`보류`로 넘어갈 때는 진행상황 표의 `미정/막힌 점`에 `backend_developer.md` §19 형식(확인 필요 대상·결정 기한)을 함께 적는다. 완료(§9) 전에 `검토 필요`·`보류` 항목이 남아 있으면 완료로 보지 않거나, 남긴 이유와 후속 처리를 명시한다.

### 진행상황 표시 형식

```markdown
## 작업 진행상황
| 단계 | 역할 | 상태 | 현재 작업 | 산출물 | 미정/막힌 점 | 다음 작업 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 |  | 진행 중 |  |  |  |  |
```

작업이 길어지면 단계가 바뀔 때마다 진행상황을 갱신한다. 미정 사항이 생기면 숨기지 않고 `미정/막힌 점`에 표시한다.

진행상황을 볼 때는 다음을 확인한다.

- 지금 어떤 역할이 작업 중인가
- 이전 단계 산출물이 다음 단계에 전달되었는가
- 미정 사항이 개발을 막는 수준인가
- 생략된 역할의 생략 근거가 남아 있는가
- 남은 검증이 무엇인가
- 즉시 피드백해야 할 오류나 반복 문제가 있는가

---

## 8. 역할 생략 기준

역할은 필요할 때만 개입한다. 다음 기준으로 생략 여부를 판단한다.

| 역할 | 생략 가능한 경우 |
| --- | --- |
| 기획자 | 요구사항이 명확하고 정책 확인이 필요 없는 경우 |
| UI/UX 디자이너 | 화면 변경이 없거나 기존 패턴 그대로 추가하는 경우 |
| 백엔드 개발자 | 프론트엔드만 변경되고 API 변경이 없는 경우 |
| 프론트엔드 개발자 | 화면 변경이 없는 백엔드 전용 작업인 경우 |

역할을 생략할 때는 "이 역할이 필요 없다"는 판단 근거를 남긴다.

## 9. 공통 완료 기준

작업은 구현만 끝났다고 완료로 보지 않는다. 다음 항목을 확인한 뒤 완료로 판단한다.

| 항목 | 완료 기준 |
| --- | --- |
| 요구사항 | 요청 목적, 포함 범위, 제외 범위가 정리되어 있다 |
| 미정 사항 | 남은 미정 사항이 없거나, 남은 이유와 후속 처리가 기록되어 있다 |
| 역할 | 필요한 역할은 작업을 마쳤고, 생략한 역할은 생략 근거가 남아 있다 |
| 구현 | 요청 범위의 구현 또는 문서 작업이 완료되어 있다 |
| 상태 처리 | 필요한 경우 로딩, 에러, 빈 상태, 권한, 예외 처리가 확인되어 있다. 책임 분담: 권한·도메인 상태값·에러코드·HTTP status=백엔드 / 각 상태의 화면·문구·다음 행동=UI/UX / 구현·에러 바운더리=프론트엔드 |
| API/DB | API, DB, 마이그레이션, 데이터 영향이 필요한 만큼 확인되어 있다 |
| 검증 | 수행한 검증과 **미수행 검증을 각각 나열**했고, 미수행에는 이유를 남겼다. 화면 변경 포함 작업은 `frontend_developer.md` §15(브라우저 주요 흐름 확인), 정책/DB 포함 작업은 `backend_developer.md` §16(테스트 우선순위)을 완료 조건으로 충족했다 |
| 운영 | 배포, 롤백, 로그, 모니터링, 데이터 보정 필요 여부를 확인했다 |
| 변경 기록 | 중요한 결정, 변경 이유, 영향 범위가 기록되어 있다 |
| 피드백 | 오류, 누락, 비효율이 있었는지 점검했고, 있으면 `feedback/feedback-log.md`에 `feedback.md` §7 표 형식으로 누적 기록했다(없으면 "특이 피드백 없음" 명시). 즉 `feedback.md` §11 파이프라인의 (A)감지·(B)누적까지 수행했다 |
| 남은 리스크 | 남은 리스크가 있으면 숨기지 않고 표시했다 |

### 완료 보고 형식

```markdown
## 완료 요약
- 작업 유형:
- 처리한 범위:
- 생략한 역할과 근거:
- 주요 변경:
- 검증: (수행 / 미수행+이유)
- 피드백: (feedback-log.md 기록 여부 또는 "특이 피드백 없음")
- 남은 미정 사항:
- 남은 리스크:
- 후속 작업:
```

작업이 작으면 완료 보고도 짧게 작성한다. 단, 검증하지 못한 항목이 있으면 반드시 이유를 남긴다.

## 10. 공통 원칙

- 각 단계는 이전 단계의 산출물을 **수신 점검**하고 시작한다. 핵심 상태값·권한·완료 조건 중 하나라도 미정이면 구현을 시작하지 않고 송신 역할로 반려한다(각 역할 문서의 "기본 작업 흐름" 1단계 참고).
- 미정 사항이 있으면 다음 단계로 넘기기 전에 해소하거나 명시적으로 표시한다.
- 단계 도중 앞 단계의 결정을 뒤집어야 하면, 영향 받는 이전 역할에게 공유한다. 작업 중 유형/원인이 바뀌면(예: 5-1 단순 오류가 정책 문제로 드러나 5-2로 전환) 진입 요약의 작업 유형·필요 역할을 갱신하고, 새로 합류하는 역할에게 지금까지의 산출물을 전달한다.
- **통합 검증(프론트-백엔드 API 계약 일치, E2E 사용자 흐름)은 프론트엔드 개발자가 주관**하고, 계약 불일치가 보이면 백엔드와 함께 해소한다.
- 각 역할의 세부 기준은 해당 역할 가이드를 따른다.
  - 기획자: `planner.md`
  - UI/UX 디자이너: `ui_ux_designer.md`
  - 백엔드 개발자: `backend_developer.md`
  - 프론트엔드 개발자: `frontend_developer.md`
- 작업 중 오류, 누락, 비효율이 발견되면 `feedback.md` 기준에 따라 즉시 피드백하거나, `feedback.md` §11 파이프라인의 (A)감지·(B)누적까지 수행해 `feedback/feedback-log.md`에 기록한다.
