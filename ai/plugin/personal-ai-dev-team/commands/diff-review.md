코드 변경분을 **side-by-side HTML diff + 변경 사유(왜)** 로 문서화한다. 목적: 리뷰어가 원본을 보지 않아도 "무엇이 / 왜" 를 한 화면에서 이해하게 한다.

## 조직 정책 게이트 (먼저 확인)

- 이 산출물은 **로컬에서 생성·로컬에서 열람**한다. 외부 서비스로 전송하지 않는다(외부 공유 제한 준수).
- diff 본문에 PII·자격증명·시크릿이 포함될 수 있으면 그대로 두지 말고, 해당 부분은 출력에서 마스킹하거나 사용자에게 알린다.

## 절차

1. **range 확정** — `$ARGUMENTS`가 비었으면 추측하지 말고 어느 범위인지 묻는다(예: `origin/<base>..HEAD`, `<시작커밋>^..HEAD`). 작업트리 미커밋 변경을 보려면 `HEAD`(=`git diff`)도 가능.
2. **변경 사유(왜) 작성** — 변경된 각 파일에 대해 "원래 어땠고 → 무엇으로 → 왜" 를 직접 작성한다.
   - **diff 본문은 절대 손으로 옮기지 않는다.** 사유만 작성한다. (본문은 git이 만든다)
   - 사유는 사이드카 JSON으로 저장한다: `{ "파일경로": "사유(여러 줄 가능)", "__summary__": "전체 변경 요약" }`
   - 파일경로 키는 `git diff --name-only <range>` 의 경로와 정확히 일치시킨다.
   - 비자명한 변경 위주로 의미 있게 적는다. 1:1 치환·자동 포맷 등은 짧게.
3. **생성** — 플러그인 번들 스크립트를 실행한다(diff 본문은 git 출력 그대로 임베드됨):
   ```bash
   node "${CLAUDE_PLUGIN_ROOT}/scripts/diff-review.mjs" \
     --range "<range>" \
     --notes "<사이드카.json>" \
     --out "docs/review/<이름>.html" \
     --title "<제목>"
   ```
4. **안내** — 생성된 HTML 경로를 알려주고, 브라우저로 열면 좌(원본)/우(변경)와 파일별 사유 박스가 보인다고 안내한다. 이 파일은 리뷰용 임시 산출물이므로 커밋 여부는 사용자가 정한다.

## 원칙

- **정확성**: diff는 git 출력만 신뢰한다. 사유 작성 시 "본문 안 보고 단정" 금지 — 필요하면 해당 파일을 Read로 대조한 뒤 사유를 쓴다.
- **사유의 결**: "무엇을 했다"가 아니라 **"왜 그렇게 했는지"**(대안 대비 트레이드오프, 정책·레이어·동작보존 이유)를 적는다.
- 자동 반영·자동 커밋 하지 않는다. 산출물 생성까지가 범위.
